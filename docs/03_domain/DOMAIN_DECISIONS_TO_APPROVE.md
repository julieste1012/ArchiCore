# Domain Decisions Requiring Business Approval

**Status:** decision register only. None of the proposals below is an approved requirement. Do not implement the proposed default until the business owner accepts it or records an alternative.

**Purpose:** reduce back-and-forth by making the remaining domain decisions explicit, showing their impact, and identifying what can safely progress in parallel.

## Decision register

| ID | Decision needed | Conflict / open question | Proposed default for review | Owner who must approve | Blocks |
|---|---|---|---|---|---|

## Implementation rules while decisions are pending

1. The proposals above do not authorize schema or behavior changes on their own.
2. Continue work that is independent of these decisions: core API hardening, validated authentication, testing, developer setup, API contract documentation and frontend interactions for existing endpoints.
3. Add a migration or state transition only after the corresponding decision has an approved status and the accepted rule is reflected in the domain specification.
4. When approved, update this register with the decision date, approver/record and resulting ADR/specification; then implement its changes with tests.
5. Do not treat a passing CI run as proof that any pending business process is complete.
